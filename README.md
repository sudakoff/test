# Semantic TextNavigator — прототип проверки условий договоров поставки

Локальное приложение для специалиста по закупкам: загружает несколько TXT-файлов (договоры,
допсоглашения, письма, проекты), строит таблицу по договорам на дату проверки — **поставщик,
сумма, срок поставки** — и для каждого значения показывает **имя файла, точную цитату и переход
к абзацу** исходного текста. Условия меняет только **подписанное допсоглашение, вступившее в силу
к дате проверки**; письма и проекты показываются отдельно как несогласованные изменения.

Внутри нет LLM и нет платных API — только правила и регулярные выражения (объяснение выбора — ниже).
Ответы, суммы, даты и имена файлов в код не зашиты: всё берётся из загруженного текста.

## Установка и запуск

Зависимости: **Python 3.10+** (используется только стандартная библиотека). Сторонних пакетов нет.

```bash
# из корня репозитория
python -m app.server            # откройте http://127.0.0.1:8000
python -m app.server --port 8080
```

Консольный вариант (тот же конвейер, удобно для проверки):

```bash
python -m app.cli documents                      # таблица, основания и ответы на 4 вопроса
python -m app.cli documents --date 2026-02-15    # другая дата проверки
python -m app.cli documents --json               # полный JSON-результат
```

Тесты (корректность данных, «нет данных», статусы документов, новый договор того же формата):

```bash
python -m unittest discover -s tests -v
```

## Сценарий использования

1. Укажите дату проверки (по умолчанию 10.03.2026), выберите TXT-файлы, нажмите **Проанализировать**
   (или **Загрузить примеры из documents/** — файлы из папки проходят тот же конвейер, что и загрузка).
2. Таблица «Договоры»: по каждому договору — поставщик, сумма, срок поставки на дату проверки.
   Под значением — ссылка «основание: файл, абз. N»; клик открывает документ справа с подсвеченным
   абзацем и выделенным фрагментом (датой/суммой). Если значение изменено допсоглашением —
   синяя метка «изменено: допсоглашение № … от …» и исходное значение.
3. Столбец «Сведения для проверки»: несогласованные изменения (письмо, проект, подписанное, но ещё
   не вступившее в силу соглашение) с цитатой; предупреждения «требует проверки».
4. Блок «Вопросы»: четыре кнопки с вопросами задания и универсальная форма (договор + поле; фильтр
   «поставка раньше даты»). Ответ содержит значение, цитату, документ-источник и несогласованные изменения.

Ответы на вопросы задания для учебного набора (`documents/`):

| Вопрос | Ответ прототипа |
|---|---|
| Срок поставки STN-101 на 10.03.2026 | **20.04.2026** — изменено ДС № 1 от 20.02.2026 (подписано, в силе); было 25.03.2026 |
| Сумма STN-102 | **2 300 000 ₽** (п. 2.1 договора); письмо поставщика о переносе срока на 15.05.2026 — не согласовано |
| Сумма STN-103 | **нет данных** — цена определяется спецификациями (п. 2.1); проект ДС с суммой 6 400 000 ₽ не подписан |
| Поставка раньше 01.04.2026 | **STN-102** (20.03.2026, есть несогласованное предложение 15.05.2026 — письмо) и **STN-103** (30.03.2026, есть неподписанный проект 30.04.2026). STN-101 — 20.04.2026 после ДС |

## Известные ограничения

* Только TXT (UTF-8 / UTF-8 BOM / Windows-1251). PDF/DOCX/OCR — вне объёма.
* Правила рассчитаны на типовую структуру русскоязычного договора: заголовок «Договор … № …»,
  «именуемое в дальнейшем „Поставщик"», пункт про сумму/цену договора, пункт со сроком поставки
  и календарной датой, подписи вида `/Иванов И.И./`. Нестандартные формулировки → «нет данных»
  или «требует проверки», но не выдуманное значение.
* Относительные сроки («в течение 30 дней с даты предоплаты») распознаются, но не вычисляются —
  показываются как «требует проверки» с цитатой.
* Статус подписания определяется эвристикой (расшифровки ФИО обеих сторон, пометка «ПРОЕКТ»,
  «не подписан»). Сканы подписей в TXT не существуют, поэтому «подписано» = «есть расшифровки».
* Если допсоглашение меняет условие частично (например, срок только по одной партии), прототип
  трактует найденную дату как новый срок — это нужно проверять по цитате.
* Суммы в формате «4.850.000» или «4 850 тыс. руб.» не распознаются (→ «нет данных»).
* Один договор = один поставщик, одна сумма, один срок. Многопартийные графики — вне объёма.

## Краткая записка

### Для какого пользователя

Специалист по закупкам, который перед совещанием/оплатой должен за минуты сверить актуальные
сумму и срок поставки по пачке договоров и не перечитывать все допсоглашения и переписку.
Ему важнее **доверие к каждому числу** (откуда взято, кем изменено), чем красота интерфейса.
Поэтому каждое значение кликабельно и ведёт в абзац источника, а всё неоднозначное помечено явно.

### Пять вопросов клиенту перед развитием решения

1. Какие ещё поля нужны в первой очереди (неустойка, предоплата, условия поставки Incoterms, валюта)?
   И каковы реальные форматы: только TXT или уже сейчас DOCX/PDF со сканами?
2. Как юридически определяется «вступило в силу» в ваших договорах: с даты подписания, с указанной
   даты, с даты последней подписи? Бывают ли допсоглашения с ретроактивным действием?
3. Как выглядят «не типовые» документы: протоколы разногласий, спецификации, которые меняют сумму?
   Должны ли спецификации считаться изменяющими условия?
4. Кто пользователь и сколько документов на один договор/в месяц; нужен ли многопользовательский
   режим и разграничение прав (поставщик видит только свои договоры)?
5. Какая цена ошибки: ложная уверенность (не заметили допсоглашение) против ложной тревоги
   (лишний «требует проверки»)? Это задаёт порог агрессивности правил.

### Принятые допущения

* Условия меняет только подписанное сторонами допсоглашение, вступившее в силу ≤ даты проверки.
  «С момента подписания» = дата документа. Если условия о вступлении в силу нет — дата документа.
* Письмо поставщика и неподписанный проект — сведения для проверки, не меняют таблицу.
* Имя файла и порядок загрузки не влияют на приоритет — только даты из текста.
* Несколько вступивших в силу допсоглашений применяются по дате вступления в силу; при одинаковой
  дате — конфликт, помечаем «требует проверки».
* Первая сумма в абзаце о «сумме/цене договора» — это и есть цена договора; абзацы с «аванс»,
  «неустойка», «оплата» штрафуются скорингом.
* Даты договора в ссылках («…№ STN-101 от 15 января 2026 г.») не считаются сроками поставки.

### Две метрики полезности/качества

1. **Точность извлечения по полям с основанием** — доля значений (сумма, срок), совпадающих с
   ручной разметкой *и* указывающих на правильный абзац; отдельно считаем долю выдуманных значений
   (должна быть 0): любое значение без цитаты — дефект.
2. **Время до проверенного ответа** — сколько секунд уходит у закупщика на ответ «какой срок по
   договору X и почему» с переходом к источнику, против чтения документов вручную; плюс доля
   строк, помеченных «требует проверки» (чем ниже при сохранении точности — тем полезнее).

### Архитектура

```
TXT-файлы ──► static/app.js (чтение в браузере, UTF-8 → cp1251 fallback)
                    │ POST /api/analyze {check_date, files[]}
                    ▼
            app/server.py  (http.server, без зависимостей)
                    │
                    ▼
            app/extractor.py — один документ → DocInfo
              • абзацы со смещениями          • тип: договор / допсоглашение / письмо
              • статус: подписан / проект / ?  • номер, ссылки на договоры, дата, вступление в силу
              • поля: сумма, срок поставки (скоринг абзацев + regex) + Evidence (абзац, цитата, фрагмент)
                    │
                    ▼
            app/resolver.py — связывание и приоритет
              • договор ← документы, ссылающиеся на его №
              • applicable / pending / check для каждого допсоглашения и письма
              • применение вступивших в силу изменений, список несогласованных, предупреждения
                    │ JSON
                    ▼
            static/ — таблица, вопросы, панель «основание», просмотр документа с подсветкой абзаца
```

`app/cli.py` — тот же конвейер из консоли; `tests/` — проверки на учебном наборе и синтетических документах.

### Три ключевых технических решения и компромиссы

1. **Правила и регулярные выражения вместо LLM.** Плюсы: детерминированность, нулевая стоимость,
   запуск без аккаунтов, каждое значение гарантированно привязано к абзацу (нет галлюцинаций),
   поведение объяснимо и покрывается тестами. Минусы: хрупкость к новым формулировкам; расширение
   на новое поле — ручная работа (но реестр `FIELD_EXTRACTORS` делает её локальной). Границы
   применимости: типовые договоры одного контура; для разнородного корпуса правила стоит дополнить
   локальной моделью как *кандидат-генератором* с обязательной проверкой цитаты в тексте.
2. **Скоринг абзацев (ключевые слова +, шум −) вместо «первое совпадение».** Позволяет отсекать
   аванс/неустойку при поиске суммы и даты оплаты при поиске срока; при равной уверенности выбирается
   более ранний абзац. Компромисс: пороги подобраны вручную, на экзотических текстах возможны
   «нет данных» там, где человек значение найдёт.
3. **Явная модель статуса документа** (`applicable / pending / check`) в резолвере, отдельно от
   извлечения. Неопределённость не прячется: подписано-но-не-в-силе, без подписей, конфликт дат —
   всё выводится пользователю с причиной. Компромисс: больше «шума» в столбце проверки, зато нет
   ложной уверенности — для закупщика это дешевле.

Стек: Python stdlib + ванильный JS — минимальная установка на машине интервьюера, никаких `pip install`.

### Что изменится при 100 000 документов и наличии прав доступа

* Извлечение переносится в **фоновую индексацию**: документы разбираются один раз при загрузке,
  результаты (`DocInfo`, абзацы, основания) хранятся в БД (PostgreSQL + полнотекстовый индекс),
  а резолвер работает по индексу, а не по пересчёту всего набора на каждый запрос.
* **Связывание по номеру** станет недостаточным: нужны нормализация номеров, дедупликация версий
  одного файла, обработка однофамильцев-договоров у разных поставщиков (ключ = номер + контрагент).
* **Права доступа**: фильтрация на уровне запроса (строки договоров и документов по ролям/подразделениям),
  аудит просмотров; цитаты показываются только из документов, к которым есть доступ, иначе
  пользователь видит «есть изменение в документе, к которому у вас нет доступа».
* Качество: очередь на ручную проверку для строк `check`, обратная связь пользователя как разметка,
  регрессионный набор из реальных документов, мониторинг доли «нет данных».
* Интерфейс: пагинация/поиск по договорам, сохранённые фильтры, экспорт в Excel.

### Три следующих улучшения (по приоритету)

1. **Ставка неустойки с цитатой** и другие поля через реестр экстракторов (предоплата, место поставки) —
   самый частый запрос закупщика, низкая стоимость благодаря архитектуре.
2. **DOCX-вход** (python-docx) и склейка строк/таблиц — реальные договоры редко приходят в TXT.
3. **Вычисление относительных сроков** («в течение N дней с даты …») с запросом даты события у
   пользователя и точечные правила для спецификаций, меняющих сумму.

## Отчёт о вайбкодинге

**Инструмент:** Cursor (агентный режим, модель Claude). Весь код, учебные документы, тесты и README
написаны агентом по текстовому заданию с последующей проверкой запусками CLI, тестов и браузера.

**Характерные запросы к ИИ:**

1. «Сделай zero-dependency прототип на Python stdlib: правила+regex, извлечение суммы и срока
   поставки с привязкой к абзацу-источнику; условия меняет только подписанное допсоглашение,
   вступившее в силу к дате проверки; письма и проекты — отдельно».
2. «Сумма договора не должна подхватывать аванс (п. 2.2 «что составляет 1 455 000 рублей») и
   неустойку — введи скоринг абзацев с отрицательными словами, проверь тестом».
3. «Проверь результат по каждому документу против исходного текста: дата документа, статус,
   ссылки на договоры — и покажи расхождения».

**Пример ошибки ИИ и как её нашли/исправили.** Первая версия `detect_doc_date` брала «первую дату в
первых 8 абзацах, кроме дат после „от"». Прогон CLI показал, что письмо поставщика получило дату
**15.05.2026** (это дата предложенного переноса, а не дата письма «Исх. № 48/26 от 2 марта 2026 г.» —
её как раз отфильтровало правило «после „от"»), а **неподписанный проект без даты** получил
**30.04.2026** из текста изменяемого пункта. Ошибку выявили сравнением вывода с исходниками;
исправление — искать дату только в «шапке» до первого нумерованного пункта и приоритизировать
строки «Исх. … от <дата>» и «г. Город <дата>»; правило «после „от"» сузили до ссылок на договоры и
доверенности. Второй пример: для STN-103 «нет данных» по сумме ссылалось на заголовок раздела
«2. ЦЕНА ДОГОВОРА…» вместо пункта 2.1 — исправлено исключением заглавных заголовков из кандидатов.
Обе ситуации закреплены тестами (`test_document_statuses_and_dates`, `test_q3_…`).

**Фактические затраты времени:** ~1 ч 20 мин чистого времени агента (документы, бэкенд, интерфейс,
тесты, README) в пределах лимита 4 часа.

**Оставшиеся задачи / не сделано:** извлечение неустойки (оставлено для изменения на встрече);
DOCX/PDF; вычисление относительных сроков; ручная корректировка значений пользователем с сохранением;
упаковка в один исполняемый файл.
